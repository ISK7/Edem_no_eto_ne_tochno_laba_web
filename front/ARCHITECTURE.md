# Архитектура клиентской части

Документ описывает устройство SPA «Едем, но это не точно». Общие команды запуска и
описание серверной части находятся в корневом [`README.md`](../README.md).

## 1. Технологии

| Слой | Технология |
| --- | --- |
| UI | React 19 + TypeScript |
| Маршрутизация | React Router 7 (`react-router-dom`) |
| Сборка | Vite 6 |
| Стили | обычный CSS с дизайн-токенами, без UI-библиотек |
| Общение с API | `fetch` в одном модуле `src/api/client.ts` |
| Состояние сессии | React Context (`AuthContext`) |
| Уведомления | собственный `ToastProvider` |

SPA не хранит access-токен в `localStorage`: он живёт только в памяти модуля API,
а refresh-токен передаётся сервером в `httpOnly`-cookie. Поэтому перезагрузка
страницы восстанавливает сессию через `POST /api/auth/refresh`.

## 2. Структура каталогов

```text
front/
├── index.html
├── vite.config.ts          # dev-сервер, proxy /api → :4000, сборка в dist
├── tsconfig.json
├── public/
│   └── favicon.svg
└── src/
    ├── main.tsx            # точка входа, BrowserRouter
    ├── App.tsx             # дерево маршрутов и провайдеры
    ├── types.ts            # общие DTO, статусы, подписи
    ├── api/
    │   └── client.ts       # единственный модуль общения с API
    ├── context/
    │   └── AuthContext.tsx # вход, регистрация, выход, восстановление сессии
    ├── components/         # переиспользуемые компоненты
    ├── pages/              # по одному файлу на страницу
    ├── utils/
    │   ├── format.ts       # даты, телефон, ФИО, склонения
    │   └── validation.ts   # клиентская валидация форм
    └── styles/
        ├── tokens.css      # цвета, тени, радиусы, типографика
        ├── index.css       # reset и базовые стили
        ├── components.css  # кнопки, поля, модальные окна, тосты, таблицы
        └── pages.css       # макеты страниц и адаптивность
```

## 3. Маршруты

| Путь | Компонент | Доступ |
| --- | --- | --- |
| `/` | `HomePage` | всем |
| `/login` | `LoginPage` | всем |
| `/register` | `RegisterPage` | всем |
| `/requests` | `RequestsPage` | авторизованным |
| `/requests/new` | `NewRequestPage` | авторизованным |
| `/admin` | `AdminPage` | только роль `ADMIN` |
| `*` | `NotFoundPage` | всем |

Защита маршрутов выполнена компонентом `RequireAuth`. Пока сессия
восстанавливается, он показывает экран «Проверяем сессию…». Если пользователь не
авторизован, происходит переход на `/login` с сохранением исходного адреса в
`state.from`. Для административных маршрутов дополнительно проверяется
`user.role === 'ADMIN'`.

## 4. Страницы

- **HomePage** — лендинг: hero-блок, схема из трёх шагов, каталог марок,
  преимущества, призыв к регистрации. Каталог, количество марок, моделей и
  автомобилей в парке подтягиваются из API.
- **LoginPage** — форма входа, показ/скрытие пароля, сообщение об ошибке
  «Неверный логин или пароль».
- **RegisterPage** — регистрация с полями логин, пароль, ФИО, телефон, email.
  Ошибки показываются под соответствующими полями; после успеха пользователь
  сразу авторизован и попадает в кабинет.
- **RequestsPage** — история заявок пользователя, сводные счётчики по статусам,
  фильтр по статусу, сортировка по дате и марке автомобиля, карточки с
  автомобилем, датой, оплатой и адресом, модальное окно с полными данными и
  причиной отклонения.
- **NewRequestPage** — создание заявки: выбор марки и модели с фиксированной
  стоимостью услуги, адрес, телефон, данные водительского удостоверения,
  дата/время, способ оплаты, согласие с правилами. Стоимость повторяется в блоке
  оплаты и в сводке. Кнопка отправки заблокирована до установки чекбокса. Справа
  (на десктопе) обновляется живая сводка заявки.
- **AdminPage** — все заявки: счётчики, поиск, фильтр по статусу, сортировка по
  дате и марке автомобиля, пагинация по 6 записей, смена статуса, обязательная
  причина отклонения, модальное окно с полными данными клиента и заявки.
  Справа от списка отображается дневное расписание с календарём, 24-часовой
  шкалой, статусными полосами и подписями моделей.
- **NotFoundPage** — страница 404 с возвратом на главную.

## 6. Модуль API

`src/api/client.ts` — единственное место, где выполняется `fetch`:

- хранит access-токен в переменной модуля;
- добавляет `Authorization: Bearer …` к защищённым запросам;
- при `401` один раз вызывает `POST /api/auth/refresh`, обновляет токен и
  повторяет исходный запрос;
- параллельные запросы используют один общий `refreshPromise`, чтобы не
  отправлять несколько refresh-запросов одновременно;
- при неудачном refresh очищает сессию и сообщает об этом через
  `setSessionLostHandler`;
- преобразует ответы об ошибках в `ApiError` с полями `message`, `fields`,
  `code`.

Публичные методы сгруппированы по смыслу: `authApi`, `catalogApi`,
`requestsApi`, `adminApi`. Компоненты не работают с `fetch` напрямую.

## 7. Состояние авторизации

`AuthProvider` при монтировании:

1. вызывает `authApi.refresh()`;
2. при успехе сохраняет пользователя в состояние и access-токен в модуль API;
3. при ошибке остаётся в гостевом режиме.

Методы `login`, `register`, `logout` обновляют состояние и корзину токенов.
`logout` вызывает сервер, чтобы отозвать refresh-токен, и очищает cookie.
Роль пользователя используется для показа ссылки на админ-панель и защиты
маршрута.

## 8. Валидация

Клиентская валидация в `src/utils/validation.ts` повторяет серверные правила:

- логин: 3–32 символа, латиница или кириллица, цифры, `_` и `-`, первый символ — буква;
- пароль: не менее 6 символов;
- ФИО: только кириллица и пробелы, минимум два слова;
- телефон: `+7(XXX)-XXX-XX-XX`;
- email: корректный адрес;
- адрес, серия и номер удостоверения, дата выдачи, дата визита и оплата —
  обязательны;
- дата визита — не раньше чем через 15 минут;
- причина отклонения — от 5 до 300 символов.

Ошибки показываются под полями, поле получает `aria-invalid`, фокус переходит к
первому невалидному полю. Серверные ошибки с `fields` также раскладываются по
полям формы.

## 9. Оформление и адаптивность

Дизайн построен на тёплой «бумажной» палитре, тёмных чернилах и оранжевом
акценте. Токены заданы в `styles/tokens.css`. Используются:

- анимации появления страниц и карточек (`fade-up`), уважающие
  `prefers-reduced-motion`;
- скелетоны загрузки и плавные состояния кнопок;
- адаптивные сетки: 1150 px, 1000 px, 940 px, 760 px, 560 px;
- на экранах до 760 px шапка упрощается, появляется нижняя панель навигации
  (`MobileTabBar`);
- проверено отсутствие горизонтальной прокрутки при ширине 390 px и высоте
  844 px; формы, карточки заявок и таблица администратора перестраиваются в
  одну колонку.

## 10. Сборка

`npm run build:web` собирает SPA в `front/dist`. В production Express отдаёт
`front/dist` и все не-API маршруты перенаправляет на `index.html`, поэтому
клиентская маршрутизация работает при прямом открытии `/admin` или
`/requests/new`.
